## 1. Actor extraction — the first thing to launch

**Why this is first.** Every grid so far moves one `depth` knob that scales the critic
*and* the policy: on `phase1_repro`, d4 is critic 1,163,520 / actor 282,888 and d32 is
8,589,568 / 2,139,400 — the actor grew 7.6× too. So "35.5 → 86.7 with depth" is a claim
about scaling both networks together, and **every headline in `results/` inherits that
ambiguity.** This resolves it without retraining a single critic, so it is the cheapest
way to firm up a result we already have.

Three grids are runnable the moment a slot frees. The QOS gives **2 jobs / 4 GPUs**, so
they must be chained — `--chain` makes them self-sequence with `afterany`, which needs
no watcher because PENDING jobs do not count against the cap.

```bash
# in this order -- antmaze_stitch is the one the headline depends on
python src/run.py experiments/extract_antmaze_stitch.yaml --write
python src/scripts/submit_packs.py --grid extract_antmaze_stitch --chain

python src/run.py experiments/extract_humanoid_navigate.yaml --write
python src/scripts/submit_packs.py --grid extract_humanoid_navigate --chain

python src/run.py experiments/extract_antmaze_navigate.yaml --write
python src/scripts/submit_packs.py --grid extract_antmaze_navigate --chain
```

| grid | source | runs | cost | status |
|---|---|---|---|---|
| `extract_antmaze_stitch` | `phase1_repro` | 12 | 68 GPU-h, ~11 h | 12/12 sources ready |
| `extract_humanoid_navigate` | `humanoid_ensemble1` | 8 | 36 GPU-h, ~6 h | 8/8 ready |
| `extract_antmaze_navigate` | `antmaze_navigate1` | 6 | 18 GPU-h, ~3 h | 6/6 ready |
| `extract_humanoid_stitch` | `humanoid_stitch1` | 8 | 36 GPU-h, ~6 h | **after §0** |

The cost column is the estimator extrapolating from *joint* training throughput. Actor-
only drops the B×B contrastive matrix entirely, so expect well under it — **but nobody
has measured it.** Worth timing the first pack and correcting the estimate.

**What to read.** All four pin `actor_depth: 4` while `depth` still selects the critic:

- **Success still climbs d4 → d32** → the gain is the **critic's**. A 4-layer policy can
  exploit a 32-layer critic, and the headline is a statement about value learning.
- **The climb flattens** → much of the gain was the deeper policy, and every headline in
  `results/` needs restating as "scaling both networks".

Two controls, both free:

- **The d4 row** is a d4 critic with a d4 actor — `phase1_repro`'s d4 cell in two stages
  instead of one. Any gap there is the two-stage-vs-joint effect, and it calibrates
  every other row. Read it before reading anything else.
- **`extract_antmaze_navigate` is a negative control.** d4 is at a 99.6 ceiling, so
  there is no headroom; if extraction does not hold ~99 there, the procedure is losing
  something and the other three readings are suspect.

**One wrinkle to remember on `extract_humanoid_navigate`:** house policy is now 0.5/0.5
for every CRL grid, but its source `humanoid_ensemble1` ran 1.0/0.0. So that extraction
moves *two* things — shallower actor AND goal sampling the joint actor never saw. A
**null result there is clean** (neither rescues the deep critic); a positive one needs a
1.0/0.0 arm to attribute. The YAML says so and how to add it.

**Trust but verify the freeze.** Every run hashes all critic arrays before and after
training and raises if they moved. Confirm it actually fired rather than assuming:

```bash
grep -h "critic verified frozen" $SCRATCH/rl-scaling/experiments/runs/extract_*/driver.log | wc -l
# want: one line per finished run
```

## 2. Interp — after extraction is queued, not before

The suite changed in three ways today and **has not been run since**, so everything in
`results/interp__critic_depth/` is from the old version.

```bash
python src/eval.py                 # plan only
python src/eval.py --submit        # 40 tasks, one job
python src/eval.py --figures
python src/eval.py --report
```

**What is new:**

1. **All seeds** (`seed_select: all`) — 40 tasks, up from 16. Metric figures now show
   mean ± 1 SD with the seeds as dots; image grids still show one seed per depth.
   `state_probes` was silently using only the *first* seed per depth via `next(...)`;
   that is fixed, and it means **the probe numbers in the current write-up may move.**
2. **Scale-free metrics** — `action_topology_gain` and `oracle_gap` now have `_norm`
   companions divided by the run's own `q_scale`. Quote those for anything cross-depth
   or cross-environment; the raw logit forms are sign-and-trend only.
3. **Eight geometry probes** (`fig7_geometry_probes`) — line, corner, wall pair (sign
   and margin), detour pair, bottleneck far side, dead end, iso-distance band. Each is a
   structure found in the maze paired with a question that has a known answer.

**Before submitting, decide whether to widen `grids:` in `src/offline/evals/evals.yaml`.**
It still lists only `[phase1_repro, humanoid_ensemble1]`. Adding `humanoid_stitch1`,
`antmaze_ensemble1` and `antmaze_navigate1` is a one-line change and is probably right —
the body-vs-data question is exactly what the critic metrics should speak to, and
`humanoid_stitch1` will have finished. Cost scales roughly linearly in tasks.

**The single number to look at first** is `detour_pair_accuracy` on `fig7`: pairs the
straight-line heuristic gets backwards, chance 0.5. On synthetic controls over this same
maze a path-distance critic scores 0.950 and a straight-line critic scores 0.256, so the
probe has real resolution. If antmaze's rises with depth while humanoid's sits at chance,
that is the sharpest statement yet of what depth buys and where it fails to.
